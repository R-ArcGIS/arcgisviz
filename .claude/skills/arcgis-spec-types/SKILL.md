# ArcGIS chart spec -> S7 types pipeline

This package builds S7 classes in R that exactly mirror the JSON config
shape (`WebChart` + a series type) that `@arcgis/charts-model`/
`@arcgis/charts-components` consume, plus the imperative JS API surface of
each `*Model` class. Everything is generated by hand-reviewed R scripts
against two local npm packages used only for type discovery:
`node_modules/@arcgis/charts-model/dist/types/**/*.d.ts` (the imperative
class API) and `node_modules/@arcgis/charts-spec/dist/json-schema/index.json`
(3MB, 620 definitions - the JSON Schema for the config shape).

## The pipeline, in order

1. **Document one model's flattened API** -> `data-raw/<model-name>.json`.
   Read the model's own `.d.ts` plus every mixin it implements (from
   `node_modules/@arcgis/charts-model/dist/types/mixins/`) and
   `chart-model.d.ts`. Flatten everything into one JSON file: every
   method/property the class actually exposes, each tagged `definedIn`
   with its source class, even though most are inherited. See
   `data-raw/bar-chart-model.json` or `data-raw/scatter-plot-model.json`
   for the exact shape (methods have `name`, `definedIn`, `async`,
   `params`, `returns`, `description`).

2. **Collect referenced spec types** into that JSON's `referencedTypes`
   array. These are the TypeScript type names the model's methods/config
   reference that live in `@arcgis/charts-spec` (not
   `@arcgis/charts-shared-utils`, which are TS-only structural types with
   no JSON Schema entry, and not types local to `@arcgis/charts-model`
   itself like `LayerInfo`/`ModelParams`/`GuideOrientation`).

3. **Resolve those types against the JSON Schema** by adding their names
   to `target_types` in `data-raw/resolve-spec-types.R`, then run it:
   `R -q -f data-raw/resolve-spec-types.R`. This writes
   `data-raw/spec-type-registry.json` (normalized shape per type: `enum`
   values/nullable, `primitive` type/min/max/multipleOf/default, `object`
   properties/required, `array`/`tuple` items, `anyOf`/`oneOf`
   alternatives, `ref` for anything not inlined) plus
   `data-raw/spec-type-dependencies.json` (every type name referenced but
   not yet in `target_types` - the deliberate next-step list) and
   `data-raw/spec-type-deferred.json` (which `deferred_types` actually got
   hit).
   - Iterate: add newly-discovered in-scope dependencies to `target_types`,
     re-run, repeat until `spec-type-dependencies.json` is empty (`[]`).
   - Deliberately excluded via `deferred_types`: FeatureLayer/
     FeatureCollection layer-definition types (`IFeatureLayer`,
     `__esri.FeatureLayer`, `ILayerDefinition`, etc. - getting dedicated
     treatment later), geometry types (`IPoint`/`IPolygon`/etc. - handled
     elsewhere), and other chart types' series shapes (e.g.
     `WebChartLineChartSeries` showing up while resolving bar chart -
     those belong to that chart type's own future pass, not this one).
   - **Known gotcha already hit and fixed**: `jsonlite::read_json()`
     defaults to `simplifyVector = FALSE`, so a JSON array like
     `["null","number"]` parses as an R *list* of length-1 strings, not an
     atomic character vector. `is.character()`/`%in%` silently no-op on a
     list instead of erroring, so nullability detection can go quietly
     wrong. The resolver's `is_nullable()`/`non_null_type()` both
     `unlist()` first - don't remove that.

4. **Extract enums** with `R -q -f data-raw/extract-enums.R` (reads the
   now-updated registry, writes `data-raw/spec-enums.json`: named
   top-level enums + every inline enum usage with a `matches_named` flag
   for exact value-set matches). Then hand-curate the final
   `data-raw/enums.json` (name -> variants): fold usages that exactly
   match a named enum's variants into that name; synthesize a
   `ParentType` + `propertyPath` PascalCase name for genuinely-unnamed
   inline enums; merge *coincidental* duplicate value-sets too (e.g.
   `IntlDateTimeFormatOptions.weekday` and
   `IntlNumberFormatOptions.unitDisplay` both being `long`/`narrow`/`short`
   became one `IntlFormatWidth`) - but only when the values are identical
   strings; a lowercase/uppercase difference (`WebChartSortOrderKinds`
   `ASC`/`DESC` vs `IStatisticDefinitionStatisticParametersOrderBy`
   `asc`/`desc`) means they're genuinely different types, not a duplicate.

5. **Write the actual `s7x::new_enum()` R files**, grouped by literal name
   prefix into `R/enums-web-chart.R` (`WebChart*`), `R/enums-intl-date-time.R`
   (`Intl*` - both DateTimeFormatOptions- and NumberFormatOptions-derived,
   since merges cross that boundary), and `R/enums-others.R` (everything
   else). One `new_enum("Name", c(...))` call per enum,
   `#' @export` above each.

6. **Write S7 classes for the resolved object types**, in dependency
   order (a class can only reference an already-defined class/enum/`Color`).
   Property types map like this:
   - `kind: "primitive"` string/number/boolean -> `s7x::class_string`/
     `class_double`/`class_boolean`.
   - `kind: "enum"` -> the matching `s7x::new_enum()`-built class from
     step 5.
   - `kind: "tuple"`, 4 numbers -> `Color` (see below), **not** a raw
     4-element vector.
   - `kind: "ref"` to another resolved object type -> that class.
   - `kind: "anyOf"`/`"oneOf"` -> `s7x::property_union(...)`.
   - Numeric-only variant sets (e.g. `fractionalSecondDigits: [1,2,3]`) ->
     `s7x::property_range_discrete(min, max)`, **not** an enum (`Enum`
     values are scalar character).
   - `kind: "array"`/no per-element type enforcement needed -> `S7::class_character`
     (string array) or `S7::class_list` (array of objects/mixed).
   - `kind: "open_object"` (`{"type":"object"}` with no `properties` in
     the spec itself, e.g. `WebChartDataItem`) or a deliberately deferred
     type (`WebChart$iLayer`, `$chartRenderer`) -> `S7::class_any`.
   - **Optionality**: a property NOT in the type's JSON Schema `required`
     array needs no special handling if it's scalar/enum - `NA`
     (`NA_character_`/`NA_real_`/`NA`) already satisfies `class_string`/
     `class_double`/`class_boolean`/`Enum` (which has `allow_na = TRUE` by
     default). Only *object-typed* optional properties need
     `s7x::property_union(Type, NULL, default = NULL)`, since there's no
     `NA` equivalent for a class instance. Required properties (whether
     scalar or object-typed) stay strictly typed with no union.

   `Color` (`R/color.R`) is a deliberate one-off exception: spec tuples
   `[r,g,b,a]` become an `r`/`g`/`b`/`a` (`class_double` each) S7 class,
   not a length-4 vector, per explicit instruction - don't "fix" this to
   match the raw tuple shape.

## Verifying property names match exactly

After writing/editing any S7 class, verify its property names against the
registry programmatically - don't eyeball it:

```r
library(S7); library(s7x)
devtools::load_all(quiet = TRUE)
schema <- jsonlite::read_json("data-raw/spec-type-registry.json")
r_props <- names(SomeClass@properties)
schema_props <- names(schema$SomeSchemaKey$properties)
setdiff(schema_props, r_props)  # missing in R
setdiff(r_props, schema_props)  # extra in R
```

Both should be `character(0)`. This has caught real naming drift before -
always run it, don't skip it because "it looks right."

## S7 class definition style

Use the `Foo := new_class(properties = list(...))` form (no explicit name
string as the first positional arg - `:=` infers it from the assignment
target; passing a name string there gets bound to `new_class()`'s `parent`
argument instead and errors confusingly). `library(S7)` at the top of each
file that uses `:=`. `s7x::` functions are always fully-qualified (no
`library(s7x)` in package R files) since `s7x` isn't formally wired into
`Imports`/`NAMESPACE` via roxygen yet.

## File load order

`R/` files have real cross-file dependencies (a type file references
classes/enums from another file). This is declared explicitly via
`Collate:` in `DESCRIPTION` - `devtools::load_all()` and `R CMD build`
both respect it. **Any new `R/` file with cross-file dependencies must be
added to `Collate:` in the correct position**, or `load_all()` will fail
with "object not found" for whatever it references from a
later-sorted-alphabetically file.

## Running R scripts

Anything that *generates or overwrites data-raw output* (resolving spec
types, extracting enums) is a real file under `data-raw/` reviewed before
running, executed with `R -q -f data-raw/whatever.R` - not an inline
`R -q -e "..."` one-liner. One-off inspection/verification snippets
(checking a class's properties, test-constructing an object, running the
property-name diff above) are fine directly via `R -q -e`.
